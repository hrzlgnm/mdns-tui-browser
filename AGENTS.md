# Agent conventions

## Workflow

- Work on a typed branch (`feat/...`, `fix/...`, `chore/...`, `refactor/...`, `docs/...`, etc.) and land changes through a pull request; direct pushes to `main` are blocked.
- Treat every task as authorizing commits and a pull request unless the user opts out. Commit each complete logical unit as soon as its applicable checks pass.
- Do not consider work complete until Validation and the two-axis Code Review (see below) have both passed; pushing or opening a PR without the review is a violation. Once review is clean, push the branch and open the pull request without waiting to be asked; pull requests are squash-merged.
- Pause for genuine forks: design tradeoffs, scope cuts, and UX or performance changes. Present the viable options and a recommendation; proceed without asking when a choice is mechanical and has one sensible answer.
- Treat every unforeseen bug, race, wrong assumption, or unhandled case as a fork. Raise it before designing or writing a fix, even when the fix seems mechanical.
- A known race, corruption risk, or correctness bug requires a real fix. If no feasible fix exists, state that directly instead of presenting the bug as an option.
- Optimize for a readable final design, not the smallest diff. Make and commit a behavior-preserving preparatory refactor first when it clarifies the behavior change; avoid speculative abstractions and redundant work.

## Validation

Before each commit, compare its complete diff with the filters in `.github/workflows/ci.yml` and run every matching local check:

| Filter or change | Local checks |
| --- | --- |
| `code` | `cargo fmt`, `cargo clippy --tests -- -D warnings`, `cargo nextest run --profile ci`, `cargo build --release`, `cargo clippy --release -- -D warnings` |
| `lint` | `cargo fmt`, `cargo clippy --tests -- -D warnings` |
| `tests` | `cargo nextest run --profile ci` |
| `aur` | `~/.local/bin/test-aur-local --variant=both` |
| Workflow or action | `actionlint` |
| `.github/renovate.json5` | `docker run --rm --volume=$(pwd)/.github/renovate.json5:/github/renovate.json5:ro --workdir=/github kokuwaio/renovate-config-validator:latest` |
| Text or documentation | `typos` |

- Install `typos` once with `cargo install typos-cli` if needed.
- Manually exercise behavior changes with `cargo run`; use `cargo run -- --service-types "_http._tcp.local.,_ssh._tcp.local."` when custom discovery types matter.
- Every commit must compile, pass its tests, and be format- and lint-clean. Do not create WIP commits that depend on a later commit to become green.

## GitHub Actions

- Set `persist-credentials: false` on `actions/checkout` unless the job pushes to the repository.
- Release builds use `cargo auditable`; preserve that audit trail when changing release workflows.

## Rust

- This is a Safe Rust project: add `#![forbid(unsafe_code)]` to every Rust file and do not add `unsafe` blocks.
- Keep imports at the top, alphabetized within standard-library, external-crate, and local-module groups.
- Use `Result<T, Box<dyn std::error::Error>>` for main functions, `Option<T>` for absent values, and `?` for propagation. Avoid `panic!` and production `unwrap()` unless failure is provably unrecoverable.
- Use `tokio::sync::RwLock` and `Arc<RwLock<T>>` for shared state and `flume` channels for async communication.
- Use `ratatui` components, `crossterm::event`, `ListState` for selection, `Frame<'_>` for rendering, `AppState` for state, and `run_tui` for the main loop. Keep UI and business logic separate.
- Keep the TUI responsive: do not block the UI thread or real-time service updates, and avoid unbounded growth in long-running sessions. Make user-facing errors clear.
- Put unit tests in `#[cfg(test)]` modules, use descriptive `test_functionality_expected_result` names, and cover edge and error cases. Put integration tests in `tests/`.
- Document public items and modules with concise `///` comments and keep every key binding documented in README.
- Fix warnings at their source; do not suppress them with `#[allow(warnings)]`.

## CLI and State Dumps

- Every new CLI option must round-trip through JSON state dumps. Add it to `AppOptions` in `src/models.rs` with `Serialize`, `Deserialize`, and `#[serde(default)]`; thread it through `AppState`, its `Clone` implementation, and `AppState::new()`; update `create_state_dump()` and `load_from_state_dump()`; test loading an older dump.
- Keep `docs/mdns-tui-browser.1` synchronized with README changes to CLI options, controls, service types, and examples. Update the `.TH` date to the current `YYYY-MM-DD` whenever the manpage changes.
- Keep the manpage focused on essential usage.

## Packaging

- For one AUR package, replace `both` in the validation command with `source` or `bin`. `--no-build` is only for generator/lint smoke tests, `--no-install` skips binary installation, and `--no-cleanup` or `--keep-dir=<path>` retains artifacts.
- `CHANGELOG.md` is generated by `git-cliff` from conventional commits using `cliff.toml` and `.github/cliff-release.toml`; never edit it or add an Unreleased section manually.
- Debian packaging uses `target/debian/changelog.gz` as `usr/share/doc/mdns-tui-browser/changelog.gz` in `Cargo.toml`. The build workflow compresses upstream `CHANGELOG.md`; do not use the Debian-format `changelog` field.
- Keep `CHANGELOG.md` in AUR packages at `/usr/share/doc/$pkgname/`, release archive staging in `build-reusable.yml`, and macOS app bundles under `Contents/Resources/`.

## Commits

- Use conventional commit subjects (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`, etc.) and `vMAJOR.MINOR.PATCH` tags.
- Keep commits meaningful, self-contained, and as small as practical. Include a behavior's tests with that behavior.
- Explain why in the commit message rather than paraphrasing the diff. Wrap body lines at 72 characters; subjects should normally stay within 80.
- Add both trailers to every commit with `--trailer`; never use `--author` or `--committer` for attribution:

  ```text
  Co-authored-by: opencode <noreply@opencode.ai>
  Assisted-by: opencode (<model-name>)
  ```

### Refining Existing Commits

- Refine work already represented by a commit with `git commit --fixup=<sha>`, including when the target is `HEAD`. Ask the user when a refinement does not map cleanly to one target.
- If the refinement makes the target message inaccurate, use `git commit --fixup=amend:<sha>`. The replacement message must begin with its own subject and repeat both attribution trailers; prefer the prefilled editor over constructing it manually.
- Keep each `fixup!` or `amend!` commit self-contained. Never amend, reorder, autosquash, or otherwise fold fixups into their targets; the user decides when to do that.

## Code Comments

- Explain non-obvious reasons for the code's current shape. Put development history and comparisons with removed alternatives in the commit message instead.
- A comment should make sense to someone seeing the current file for the first time. If it would not be written from scratch, remove it.
- Match neighboring routine call sites: an ordinary helper call does not need a comment when equivalent calls are uncommented.

## Code Review

This is a mandatory gate. Do not push, do not open a PR, and do not
declare a task complete until the two-axis review has run and its
findings are fixed.

- **When:** after Validation passes on the final commit(s), before
  `git push` and before `gh pr create`. Re-run after every fixup that
  touches `src/`, `tests/`, or docs.
- **How:** load the `code-review` skill (skill tool `name: "code-review"`).
  Pin the fixed point to `main` (use `origin/main` if `main` is stale)
  and pass `git diff main...HEAD` (three-dot, merge-base) plus
  `git log main..HEAD --oneline`. The skill spawns two parallel
  sub-agents — **Standards** (this file plus the Fowler smell baseline
  defined in the skill) and **Spec** (originating issue/spec/request;
  reports "no spec available" if none exists) — then aggregates.
- **Report:** paste both axes verbatim under `## Standards` / `## Spec`,
  do not merge or rerank them. End with a one-line summary: total
  findings per axis and the worst issue within each axis. Fix defects
  before pushing.
- After adding changes to an open pull request, update its description
  so the summary, issue references, and testing cover the cumulative
  branch.
